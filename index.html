climate explorer (made with Claude)

An interactive map of thirty-year climate normals across the United States, Canada and Europe — 4,950 regions, fourteen metrics, month by month.

Climate Explorer is an interactive map tool for visualizing climate data down to county level. Every metric colors the map according to a color gradient, then lets you examine any one of them for a monthly breakdown. The project was inspired by attempts to optimize for the age-old question of "where is the weather nice, and for how much of the year?", but grew into a more general purpose tool.

What it does

Climate Explorer mode

The default mode shades the map by one metric at a time. An Annual/Monthly toggle steps through individual months with a slider or autoplays them as an animation, which lets you visualize seasonal phenomena like the North American monsoon or the west coast rainy season. Fourteen metrics are available across three groups:

  • Precipitation — precipitation, precipitation days, snowfall, snow days
  • Atmosphere — dew point, relative humidity, cloud cover, sunshine hours
  • Temperature — average high, average low, mean, diurnal range, frost days, hot days

Clicking any region opens a detail popup with the monthly series behind every metric, either focused on the current one or as a full grid.

Comfortable Days mode

In this mode, you can set an arbitrary list of requirements for what constitutes a "comfortable day" - a temperature range, dew point ceiling, precipitation, snowfall, cloud cover - and the map gets colored in by how many days a year satisfy all the conditions.

Four map views

Each region set gets a projection appropriate to its latitude rather than one global compromise.

US only
Albers USA composite — lower 48 with Alaska and Hawai‘i insets · 3,143 counties
North America
Albers conic, standard parallels 30°/60° · US counties + Canadian census divisions
Canada
Lambert conformal conic, parallels 49°/77° · 293 census divisions
Europe
EPSG:3035, pre-projected from Nuts2json · 1,514 NUTS-3 regions

Where the data comes from

A good part of the work for this project was actually not the map UI but instead the task of assembling a single coherent dataset out of three national and supranational sources that disagree about periods, units, station density and what counts as a hot day.

United States
NOAA Climate Normals 1991–2020, fetched through the ACIS/NCEI API and inverse-distance-weighted to county centroids
Canada
ECCC Climate Normals 1981–2010, IDW to census division centroids
Europe
ERA5 monthly averaged reanalysis 1991–2020 from the Copernicus CDS, regridded to NUTS-3
Cloud & sunshine
NASA POWER satellite reanalysis where no station observations exist

How it is built

Vanilla JavaScript with D3 v7 and TopoJSON, a single index.html entry point and one app.js, no build step and no bundler. Geometry is pulled from CDN at runtime (us-atlas and Nuts2json); the climate data itself is precomputed into static JSON so the app loads without a backend. Around thirty Python scripts were written the fetching, interpolation and patching offline.

Proof Trainer (made with Claude)

An in-browser tool for learning formal logic: four proof systems, a Kripke model editor, and a Curry–Howard panel that shows you the program hiding inside your proof.

As a child of the digital era, I was always frustrated by how slow traditional education was to adopt the new tools that are available. Math/logic is a prime candidate for this kind of thing - correctness is computer-verifiable, and solution traces often consist of a discrete chain of steps that can be mechanically checked. To be fair, this project was inspired by an existing university course website with an interactive JS-based proof builder; this one just goes much further, handling not just fitch-style propositional ND but also sequent calculus, Hilbert style calculus, and first-order logic. The curriculum also emphasizes the nuances of intuistionstic vs. classical logic where they appear; the strength required to prove a given problem is always given, and in some cases, the task of showing a statement that is classically valid but intuionistically unprovable is the whole deal.

The systems

Natural deduction
Fitch-style, scope-aware, with nested subproofs and eigenvariable boxes for ∀I and ∃E
Sequent calculus
LK for classical and LJ for intuitionistic, built bottom-up as a tree
Hilbert system
Axiom schemas plus modus ponens and generalisation, on flat numbered lines
Hilbert + DT
The same axioms with the deduction theorem as a Fitch-style closer
Kripke semantics
A click-to-build poset editor for reading off forcing and constructing countermodels

Every system supports both intuitionistic and classical logic, with the relevant rules surfaced or hidden per problem, and the propositional core extends to first-order logic — quantifiers, predicates, terms and eigenvariable side conditions — in all four proof systems.

Countermodels, not just failure

Showing that a statement is false in classical logic is easy - just find a truth assignment where the statement doesn't hold. On the other hand, to show a statement has no proof in intuitionistic logic, the standard approach is to build a Kripke countermodel, which the app features in its own part of the curriculum with an interactive model builder.

Intuitionistic logic is notable for having a "richer" structure than classical logic. For example, in classical logic, a consequence of LEM is that ¬¬p ⊢ p holds, meaning irrefutable statements are always provable - this is intuitive enough. In IL, however, it's more complicated - you can find statements, like instances of LEM itself p ∨ ¬p, where you can prove the negation of the negation of the statement, but not the statement itself; i.e., ⊢ ¬¬(p ∨ ¬p), but ⊬ p ∨ ¬p.

Curry–Howard

A toggleable side panel mirrors every natural-deduction and Hilbert proof as a typed λ-term, line for line, including dependent Π and Σ types for first-order goals. Implication introduction becomes lambda abstraction, conjunction becomes a pair, disjunction becomes a sum with inl/inr, and case analysis becomes a case expression.

How it is built

Vanilla JavaScript ES modules with no dependencies and no build step; a small bundled dev server exists only because ES modules will not load over file://. Each proof engine is a standalone module that knows nothing about the DOM, and the UI dispatches per system — adding a new logic means writing an engine plus its render and control functions, and nothing else moves.

Correctness is enforced by three Node test suites: one over the parser, all four engines, the first-order machinery and the Curry–Howard translation; one that replays every authored curriculum solution and checks the proof actually closes; and one over the Kripke editor, validator and explainer.

ftvt

Fourier transform visualization tool — symbolic signals in, spectrum out, with a slider you can drag while watching both plots move.

ftvt is a tool for visualizing Fourier transforms in one dimension. Signals are entered as mathematical expressions in symbolic notation, which are then parsed into evaluable functions, sampled over an interval, sent through the FFT algorithm, and finally plotted side by side with the original signal. By default, the plots in both the time domain and the frequency domain are updated automatically whenever the entered expression is edited. A key feature is the Desmos-style "slider" feature that allows you to smoothly adjust a parameter of the signal while viewing the effects to the transformed function in real time. There is also a filtering function with low pass, high pass, band pass, and band stop filters which works in much the same way.

Implementing complex arithmetic and FFT in JS

The FFT makes use of certain properties of the complex exponential function in order to break down the task recursively and enable an \( O \left( n \log n \right) \) runtime, so the ability to perform operations on complex numbers will be needed by the implementation. Javascript lacks built-in support for complex numbers, but we can work around this by using an ordered pair (actually an array of length 2) to represent the real and imaginary parts of a complex number.

\[ z = x + iy \Longleftrightarrow [x,y] \]
function cplx(re, im) {
  return [re, im];
}

function cplxFromReal(re) {
  return [re, 0];
}

All the mathematical operations needed by the algorithm were then implemented manually. Addition and subtraction are simple termwise vector operations. Multiplication and division are slightly more involved, but the formulas are straightforward to derive.

$$\begin{aligned} z_1 + z_2 &= (a + bi) + (c + di) \\ &= (a + c) + i \left( b + d \right) \\ \\ z_1 - z_2 &= (a + bi) - (c + di) \\ &= (a - c) + i \left( b - d \right) \\ \\ z_1 \times z_2 &= (a + bi) (c + di) \\ &= ac + bci + adi - bd \\ &= (ac - bd) + i \left( bc + ad \right ) \\ \\ \frac{z_1}{z_2} &= \frac{a + bi}{c + di} \\ &= \frac{a + bi}{c + di} \cdot \frac{c - di}{c - di} \\ &= \frac{ac + bci - adi + bd}{c^2 + d^2} \\ &= \frac{\left( ac + bd \right) + i \left( bc - ad \right)}{c^2 + d^2} \\ &= \left( \frac{ac + bd}{c^2 + d^2} \right) + i \left( \frac{bc - ad}{c^2 + d^2} \right) \end{aligned}$$
function cplxAdd(z1, z2) {
  return cplx(z1[0] + z2[0], z1[1] + z2[1]);
}

function cplxSub(z1, z2) {
  return cplx(z1[0] - z2[0], z1[1] - z2[1]);
}

function cplxMul(z1, z2) {
  var a = z1[0];
  var b = z1[1];
  var c = z2[0];
  var d = z2[1];
  var re = a*c - b*d;
  var im = b*c + a*d;
  var res = cplx(re, im);
  return cplx(re, im);
}

function cplxDiv(z1, z2) {
  var a = z1[0];
  var b = z1[1];
  var c = z2[0];
  var d = z2[1];
  var dn = c*c + d*d;
  var re = (a*c + b*d) / dn;
  var im = (b*c - a*d) / dn;
  return cplx(re, im);
}

A formula to compute the complex exponential function can be derived using Euler's formula, making use of the real-valued exponential, cosine, and sine functions.

$$\begin{aligned} e^z &= e^{x + iy} \\ &= e^{x} e^{iy} \\ &= e^{x} (\cos y + i \sin y) \\ &= e^{x} \cos y + i \left(e^{x} \sin y \right) \end{aligned}$$
function cplxExp(z) {
  var x = z[0];
  var y = z[1];
  var ex = Math.exp(x);
  var re = ex * Math.cos(y);
  var im = ex * Math.sin(y);
  return cplx(re, im);
}

Implementing the FFT

The Discrete Fourier transform (DFT) \( X_k \) of a discrete function \( x_n \), i.e. a sequence \( \mathbb{N} \rightarrow \mathbb{R} \) or \( \mathbb{N} \rightarrow \mathbb{C} \), is defined as follows:

$$ X_k = \sum _{n=0} ^{N-1} x_n \cdot e^{-i 2 \pi \frac{k}{N} n} $$

By translating the summation to a simple for loop, we can derive a "brute force" way to compute the DFT of a function, which we will also refer to as the "DFT". This naive implementation is \( O(n^2) \) and therefore not suited for large inputs, but it will still serve an important role as the recursive base case of the FFT.

function dft_generic(xs, inverse) {
  var N = xs.length;
  var ys = [];
  for (var k = 0; k < N; k++) {
    var acc = cplxFromReal(0);
    for (var n = 0; n < N; n++) {
      var n0 = inverse ? 2 : (-2);
      var n1 = cplxFromReal(n0);
      var n2 = cplxMul(n1, cpi);
      var n3 = cplxMul(n2, j);
      var n4 = cplxFromReal(n);
      var n5 = cplxMul(n3, n4);
      var n6 = cplxFromReal(k);
      var n7 = cplxMul(n5, n6);
      var n8 = cplxFromReal(N);
      var n9 = cplxDiv(n7, n8);
      var n10 = cplxExp(n9);
      var n11 = cplxFromPair(xs[n]);
      var n12 = cplxMul(n11, n10);
      var n13 = cplxAdd(acc, n12);
      acc = n13;
    }
    ys.push(acc);
  }

  return ys;
}

(Since Javascript lacks support for operator overloading, the code for complex valued arithmetic had to be manually "unrolled" and ended up being rather verbose, but this is probably unavoidable with the choice of language.)

Notice that there are actually two nested for loops in the preceding code. This is because the definition computes the DFT of just a single point of the input, and so obtaining the DFT of the entire input would require another layer of iteration - hence the \( O(n^2) \) running time.

The full FFT divides the input into the even numbered and odd numbered points, and the routine is then called recursively on each of them. The key insight of the algorithm then allows the results of the recursive calls to be reassembled into the transform of the entire input.

function fft_generic(xs, inverse) {
  var N = xs.length;

  // base case: do a brute force dft on length 2
  if (xs.length == 2)
    return dft_generic(xs, inverse);

  var ys_half1 = [];
  var ys_half2 = [];

  var [evens, odds] = separateOddsEvens(xs);

  var Es = fft_generic(evens, inverse);
  var Os = fft_generic(odds, inverse);

  // the "key" reassembly step
  for (var k = 0; k < (N >> 1); k++) {
    var n0 = inverse ? 2 : (-2);
    var n1 = cplxFromReal(n0);
    var n2 = cplxMul(n1, cpi);
    var n3 = cplxMul(n2, j);
    var n4 = cplxFromReal(k);
    var n5 = cplxMul(n3, n4);
    var n6 = cplxFromReal(N);
    var n7 = cplxDiv(n5, n6);
    var R = cplxExp(n7);
    var Ek = Es[k];
    var Ok = Os[k];
    var ROk = cplxMul(R, Ok);
    var yk1 = cplxAdd(Ek, ROk);
    var yk2 = cplxSub(Ek, ROk);
    ys_half1.push(yk1);
    ys_half2.push(yk2);
  }

  var ys = ys_half1.concat(ys_half2);
  return ys;
}

rjx

A realtime logic circuit simulator in C, with a timeline you can step frame by frame — forwards or backwards.

rjx is a realtime logic circuit simulator, inspired by computational redstone. It gives you fine control over the simulation timeline, including the ability to go frame by frame and to run the simulation in reverse. There is a small set of basic components including basic logic gates, button/switch inputs, and several kinds of seven-segment style displays. The GUI is minimal and much of the functionality is accessed through predetermined keybinds.

Note: rjx does not simulate real life digital circuits. It should be considered more of an educational or hobbyist application for the exploration of constructing abstract machines from a simple set of logical components.

Hash tables in C

The C standard library is limited and lacks support for common data structures like linked lists and binary trees. This necessitates either using a third party library or rolling your own library, and I usually go with the latter, partly as an educational exercise and partly so that I can understand how the library works intuitively and I don't have to decode obscure documentation. In this project, since components can be selected graphically on screen, a hash table was used to quickly map from screen coordinates to the corresponding object in memory. The hash function itself was sourced from the internet more or less verbatim, since deriving a good hash function is mathematically involved and well beyond the scope.

In memory, hash tables exist as just contiguous blocks of data. For this implementation, they were created as a dynamically allocated struct that was mostly occupied by a buffer of 8-byte words, along with some metadata about the load factor.

typedef struct {
  uint64_t *bfr;
  int bkts;
  int entries;
} hmap_tx;

typedef struct {
  uint64_t key, val;
} hmap_entry_tx;

The bulk of the work was creating a set of routines for accessing the data structure and automating its memory allocation. My personal convention for implementing data structures in C is to create standard constructor and destructor patterns for managing the lifetime of the object, so the responsibility falls on the calling routine to know when the object is no longer needed, although in other respects the process is automated, and destructors can recursively call other destructors to simplify the cleanup process. The library also takes care of resizing the hash table once a certain load factor has been reached and rehashing automatically.

static void hmap_init(hmap_tx *h, int bkts) {
  int bytes = BYTES_PER_BKT * bkts;
  h->bfr = malloc(bytes);
  ...
}

static void hmap_bfr_destroy(uint64_t *bfr, int bkts) {
  ...
  free(bfr);
}

static void hmap_destroy(hmap_tx *h) {
  hmap_bfr_destroy(h->bfr, h->bkts);
}

I opted to use preprocessor macros to allow hash tables to be created as "instances" for individual types. C lacks true generics, but we can use macros as an ugly, if functional, workaround to emulate parametric types. Despite the clunkiness, it's still preferrable to the alternative, which is to create data structures with (void*) pointers that are then casted to various other types, but this is extremely type-unsafe and in my experience leads to painful debugging sessions of trying to pin down the cause of segmentation faults. This can be easily avoided by just initializing a different "instance" of a data structure for each needed type, even if it technically counts as code repetition.
